# OMAP4460 Boot ROM USB memory-sink audit

Offline review of this Touch 10's 49,152-byte ROM dump, SHA-256 `7fd0176dbdf06cfa42f147a5c0a923abb1f2fa269b82d0352fa02a5bd3b8efff`. Addresses are the ROM's `0x30000` low alias. I used the saved binary and IDA database; I made no device command, USB transfer, or device-state change. This extends [the earlier USB audit](bootrom-usb-audit-2026-11-07.md) with the actual DMA mode, memory-copy sinks, transfer lifetime, and reset paths.

Later [controller review](bootrom-usb-dma-reset-followup-2026-11-07.md)
confirmed the ROM's hardware RX mode 1: a four-byte GET_ID packet on the
512-byte endpoint uses the CPU residual FIFO copy. The live reset result
therefore did not test a DMA memory write.

## Result and trust boundary

No pre-authentication USB memory corruption or arbitrary ROM readback is established by these instructions. The visible peripheral boot receiver programs **ROM-selected** destinations and lengths: four bytes for a header/length field, then at most `0x7fff` bytes for type 2 or `0xbfff` for type 3 (`0x3317e`–`0x3318c`, `0x33200`–`0x33218`, `0x33254`–`0x33270`). The first four-byte destination originates at the caller's stack slot (`0x30b7e`–`0x30b8a`); the next four-byte destination is a stack slot within `0x33092` (`0x33200`–`0x33218`). The host controls the bytes and the declared body length, but the latter is checked against `0x4030bfff - R7`, with `R7=0x40304000` or `0x40300000` (`0x330d6`–`0x330e2`). The ROM's receive-descriptor field `+0x14` is set to **1** at `0x33148`. Accordingly, these pre-authentication receives select the DMA branch at `0x351f6`–`0x35226` and `0x35bd2`–`0x35c04`; the software FIFO branch at `0x354dc` is an alternate ROM API path.

The main unresolved boundary is the controller's behavior under malformed bulk packets and mid-transfer cancellation. ROM code programs a DMA byte count, but a binary-only review cannot prove that this MUSB implementation never writes beyond `DMA_COUNT` after a short, long, or interrupted transfer. No evidence yet shows such an overrun. The only TI OMAP4460 ES1.x HS USB OTG erratum identified in [TI's Rev H errata](https://www.ti.com/pdfs/wtbu/OMAP4460_ES1.x_Silicon_Errata_Rev_H.pdf), i661, concerns software-initiated ULPI PHY accesses corrupting **TX** traffic or halting communication; it is not evidence of an RX count bypass.

## Host input to memory sinks

| Sink | ROM evidence | Bound and outcome |
| --- | --- | --- |
| EP0 setup buffer | `0x35ab0`–`0x35aea` reads two FIFO words and writes exactly eight setup bytes at `0x4030dc3e`–`0x4030dc45`. `0x35aec`–`0x35b00` checks that RXCOUNT is nonzero, not that it is eight. | Host `wLength` never becomes the setup copy size. A controller-delivered short SETUP could cause stale/missing FIFO bytes to be interpreted, but the subsequent handlers use fixed state and descriptor choices. Whether this controller delivers malformed SETUP packets is unproven. |
| EP0 IN descriptor read | `0x35900`–`0x359c0` selects fixed ROM or initialized SRAM descriptors, then `0x359c2`–`0x359ca` caps the reply to `min(descriptor_length, wLength)`. `0x3556e`–`0x355ca` sends at most 64 bytes per EP0 packet, incrementing its source by exactly bytes sent. | No host-supplied pointer. For the indexed string table `0x358aa`–`0x358fc`, indexes `0x20`–`0x2b` map to twelve 50-byte slots in `0x37bf4`–`0x37e4c`. Their first-byte lengths are `8,36,12,18,18,18,28,34,8,8,0,0`, each at most 50. Other fixed replies at `0x37e56`, `0x37e88`, `0x37eba`, and `0x37eec` have lengths 8, 4, 8, and 8. Unknown indexes use the fixed fallback. Thus a large `wLength` does not walk past a descriptor. |
| EP0 OUT requests | `0x35a00`–`0x35aae` dispatches requests 1, 3, 5, 9, 11 to status/feature/address/configuration handlers; unsupported requests stall. `0x35b04`–`0x35b6e` handles EP0 stages. | These handlers update fixed USB state/controller registers. There is no data-stage routine copying host-chosen OUT bytes to a supplied address. Permissive `bmRequestType` checks may affect protocol behavior but do not expose a memory pointer here. |
| Bulk RX DMA | `0x34288`–`0x342b8` installs `[desc+8]` as start/current and `[desc+0xc]` as requested count in `0x4030dbec+0x14/+0x18/+0x1c`. `0x35226`–`0x3526c` writes the destination to `0x4a0ab218`, count to `0x4a0ab21c`, then enables the DMA channel at `0x4a0ab214` and RXCSR. | Both pointer and count originate in the ROM caller. On the visible path, the count is 4 or checked below 49,152. The count register is the primary hardware memory-write bound; the ROM does not inspect every DMA write individually. |
| DMA channel interrupt | The dedicated interrupt entry `0x352ea`–`0x3535a` reads DMA interrupt status at `0x4a0ab200`. RX bit 1 takes `0x3530a` onward: if RXCOUNT is zero, it clears DMA control bits 0/3 and marks the descriptor complete (state 0, `0x35344`–`0x35352`); if RXCOUNT is nonzero, it clears RXCSR DMA enable, clears DMA control bits 0/3, and marks an error (state 1, `0x35316`–`0x35342`). It then calls `[desc+4]` if nonzero. | This handler performs no CPU memory copy and no independent transferred-byte comparison; it relies on the programmed DMA count and controller completion. It dereferences the current descriptor without a null/state guard, so a late interrupt after cleanup is a conditional lifetime/fault concern, not a host-chosen branch target on this path. |
| Bulk RX residual FIFO copy | `0x35454`–`0x354da` checks active descriptor state 4, computes `((DMA_ADDR - start) + RXCOUNT) & 0xffff` at `0x35488`–`0x35498`, and calls the word/byte FIFO copier `0x3541a` only when this equals the requested count (`0x3549a`–`0x354b2`). | If the controller honors its programmed count, `0 <= DMA_ADDR-start <= requested`, and RXCOUNT is at most the configured maxpacket, then the sum is at most `49,151+512=49,663`, so the 16-bit cast cannot wrap. Equality means the residual copy exactly fills the remaining requested bytes. On mismatch the ROM stalls and changes state before invoking a callback; it does not copy residual bytes. The hardware premises remain to be verified separately. |
| Alternate bulk RX software FIFO copy | `0x354dc`–`0x3556c` checks descriptor state 4; `0x35514`–`0x35526` computes `(current-start+RXCOUNT)&0xffff` and compares it to requested count **before** calling `0x3541a` at `0x35536`–`0x35538`. It increments current by RXCOUNT at `0x35548`–`0x3554c`. | With the same visible length and maxpacket bounds, there is no 16-bit wrap, and the guard prevents a write past the ROM-selected requested region. This branch is not chosen by the generic pre-authentication image receiver, which set descriptor mode 1. |
| Bulk TX source read | `0x33058`–`0x33076` sends 0x51 or 0x46 bytes from the fixed `0x4030db8c` workspace, ending before USB state at `0x4030dbec`; its calls are `0x33164` and `0x331e4`. `0x34258`–`0x34284` and `0x3518a`–`0x351f4` set fixed source/length and DMA transmit registers. The alternate FIFO copier `0x35130`–`0x35188` sends `min(remaining, TXMAXP)`. | No host-supplied TX source pointer. `0x3515c` can load a whole word for a 1–3 byte tail, but `0x35164`–`0x3517a` emits only the selected tail bytes. This is a bounded internal over-read for the visible fixed sources, not a byte leak or host-directed ROM read. |
| Completion/event callback | DMA IRQ `0x35352`–`0x3535a`, RX `0x354d0`–`0x354da` / `0x35562`–`0x3556c`, and TX `0x353bc`–`0x353c2` / `0x3540c`–`0x35416` branch through `[desc+4]` only if nonzero. The generic receiver clears that field at `0x33140`, `0x33210`, and `0x33268`. Event callback slot `0x4030dbec+0x2c` is initialized to ROM `0x340ce+1` at `0x3412a`–`0x34132`; registration API `0x342ba`–`0x342f2` can replace it only for code already executing on the device. | USB packets cannot choose these branch targets through the reviewed setup or bulk parser. A different on-device ROM API caller can supply its own pointers, outside this pre-authentication boundary. |

The endpoint setup at `0x3571e`/`0x3572c` programs 512-byte high-speed or 64-byte full-speed maximum packets into TXMAXP/RXMAXP at `0x3572e`–`0x35732`. The arithmetic proofs above depend on RXCOUNT reflecting a packet no larger than that hardware setting. They do **not** claim that the ROM independently validates a corrupt controller-reported RXCOUNT.

## Cancellation and residual state

The following ROM transitions are worth retaining as *conditional* leads, not completed exploit claims:

1. **USB bus RESET:** `0x35bb6`–`0x35bbe` tests INTRUSB bit 2, sets the USB state byte at `0x4030dc38` to 2, and exits at `0x35c34`. It does **not** change an active send/receive descriptor's state or explicitly cancel DMA. A host reset during a receive therefore leaves software descriptor state 4 until later completion or cleanup. The first receive destination is on the caller's stack (`0x30b7e`–`0x30b8a`). On a timeout/error, `0x332c4`–`0x332d6` invokes transport close and returns to that caller. Close calls `0x35274`, which disables endpoint/USB interrupts (`0x35276`–`0x3528c`), flushes FIFOs, and clears POWER.SOFTCONN (`0x352da`–`0x352e0`), so ordinary *new* host packets cannot arrive after close. If an already queued transfer or controller fault allowed DMA to write after the stack frame was reused, it could corrupt control data even though `DMA_COUNT` is four. No such late write has been observed, and the hardware's treatment of pending DMA on reset/disconnect is unanswered.
2. **Role-loss/DEVCTL path:** The separate branch at `0x35ba4`–`0x35bb4` examines DEVCTL bits and can reach `0x35c1c`, which calls `0x35274` and marks one active descriptor as state 1 (`0x35c20`–`0x35c32`). It checks send first and receive only if send is not active. If a different ROM API caller has both active, receive remains state 4. The generic pre-authentication image flow sends and receives sequentially (`0x33058`, `0x3317e`–`0x331ae`, `0x331de`–`0x33270`), so no such concurrent-send/receive instance was found on that path.
3. **Configuration zero:** `0x356e2`–`0x357e2` accepts SET_CONFIGURATION while state 3 or 4. The zero case at `0x35798`–`0x357de` clears endpoint registers, maxpacket, and FIFO state, but does not set an active receive descriptor's state to 1 or 0. This could leave software believing that an in-flight receive remains active if the host deconfigures and reconfigures quickly. The ROM still retains the same ROM-selected destination/count; the memory effect depends on MUSB behavior after endpoint reset.
4. **DMA channel cancellation:** Neither the role-loss/cleanup helper `0x35274`–`0x352e8` nor the zero-configuration branch explicitly clears DMA channel control at `0x4a0ab214`; the bus RESET branch does not call `0x35274` at all. Normal successful DMA completion does clear bits 0 and 3 at `0x354c2`–`0x354c8`. For comparison, the [upstream Linux MUSB DMA abort routine](https://github.com/torvalds/linux/blob/master/drivers/usb/musb/musbhsdma.c#L1452-L1518) explicitly clears RXCSR DMA mode/enabling, DMA control, address, and count. That is evidence of a software abort sequence, not proof that this OMAP controller retains DMA across a hardware bus reset. RXCSR/FIFO reset or the controller's own bus-reset handling may halt it implicitly. A host-timed reset around a four-byte receive is therefore a hardware/lifetime hypothesis, not a verified buffer write.
5. **Rearm ordering:** `0x342a0`–`0x342b2` publishes the receive descriptor and state 4 before writing the new count/start/current and enabling DMA. A pending RX interrupt in that short window could observe old transfer state. On a normal completed transfer, the previous DMA completion clears descriptor state (`0x354ca`–`0x354ce`), and a new packet compared against the old completed count does not satisfy the residual-copy equality. In an interrupted transfer, the exact result again depends on the endpoint/DMA pending state; no host-controlled destination follows from the ordering alone.

These transitions may yield a transport stall or reset-sensitive fault. I did not find a ROM instruction that turns them into an arbitrary pointer, an unbounded CPU FIFO copy, or arbitrary ROM readback on the tested pre-authentication route. A meaningful next check is to establish the exact MUSB DMA mode-1 behavior for `DMA_COUNT=4` and reset/reconfiguration from a controller specification or a RAM-only, instrumented test; this report does not assume either answer.
