# Touch 10 OMAP4460 Boot ROM: USB boot state machine

Offline analysis of this panel's 48 KiB ROM, `analysis/bootrom/omap4460-bootrom-lowalias.bin` (SHA-256 `7fd0176dbdf06cfa42f147a5c0a923abb1f2fa269b82d0352fa02a5bd3b8efff`). Addresses are low-alias execution addresses. No device command, USB test, or storage write was made for this review. This traces sequencing and error behavior; the separate [USB audit](bootrom-usb-audit-2026-11-07.md) covers EP0 descriptors and receive arithmetic, and the [CH audit](bootrom-ch-parser-2026-11-07.md) covers the configuration-header handlers.

Later [live reset evidence and controller review](bootrom-usb-dma-reset-followup-2026-11-07.md)
showed that four-byte GET_ID packets take the residual FIFO path under this
ROM's RX DMA request mode 1. The reset test does not resolve DMA enable or
memory writes during a full-packet receive.

## Entry and accepted commands

The boot-source chooser calls `0x33092` from `0x30b8a` for peripheral sources `A`–`G`. Sources `E`–`G` select the same USB vtable at `0x37730..0x37768`: open `0x340e2`, receive `0x34288`, send `0x34258`, close `0x34074`. The source code, vtable, and receive descriptor are chosen inside ROM, rather than through a USB request. The image destination is `0x40304000` for type 2 (`0x330e0`) or `0x40300000` for type 3 (`0x330dc`). The captured panel is the type-2 high-security path.

After USB configuration 1 sets the device state to 4 (`0x35782..0x35784`), the caller arms exactly four bytes into the chooser's command word (`0x3317e..0x3318c`). The parser at `0x331cc..0x331d6` accepts only these little-endian values:

| Command | Bytes on bulk OUT | Result |
| --- | --- | --- |
| `0xf0030003` GET_ID | `03 00 03 f0` | Send the ROM-generated ASIC ID, then arm another four-byte command receive. |
| `0xf0030002` BOOT | `02 00 03 f0` | Arm a four-byte length receive, followed by one image receive. |
| Anything else | Any other four-byte value | Enter common error cleanup; no image receive. |

GET_ID's send helper `0x33058` reads the fixed ID buffer at `0x4030db8c`, selects 81 bytes by default or 70 when the first ID byte is 4, and waits for completion (`0x3305c..0x33090`). The recorded USB transfer returned an 81-byte ID in `rom-signed-mlo-usb-chunked-2026-11-06.log`. The branch at `0x331f2..0x331f6` returns to the command receive after each successful GET_ID. Register R9 is set to zero at `0x33176` and has no nonzero assignment in this function, so the apparent alternate branch to BOOT is not reachable through an ordinary GET_ID. A host can repeat GET_ID indefinitely while keeping each exchange within its timeout; that prolongs ROM USB availability but supplies neither an address nor an arbitrary read primitive.

BOOT causes a *new* four-byte receive into a stack length word (`0x33200..0x33218`). At `0x3324e..0x3325e`, the ROM requires successful completion, nonzero length, and `length <= 0x4030bfff - destination`. The resulting maximum is **32,767 bytes** on this type-2 unit, or 49,151 on type 3. Only then does it arm the image receive at `0x33260..0x33270`. BOOT is a one-way transition: a subsequent GET_ID word at the length stage is rejected as a huge length, and GET_ID bytes inside the body are ordinary image bytes. The command word is not interpreted again after BOOT.

## Receive completion, short packets, and timeouts

The descriptor is initialized with `descriptor[0x14] = 1` at `0x33146..0x33148`. `0x34288` installs its pointer, count, and destination in USB state at `0x4030dbec + 0x10/+0x1c/+0x14` and sets status 4 (pending). Since that descriptor flag is one, `0x351f6..0x3526c` arms the **DMA** receive path for this ROM caller, including the checked count and fixed destination in the USB DMA registers at `0x4a0ab218/0x4a0ab21c`. The FIFO-only handler `0x354dc` exists for other ROM API callers but is not the normal pre-authentication command/image path here.

On DMA completion, the USB interrupt path calls `0x35454` from `0x35c00`. It computes `DMA_current - destination + residual_RXCOUNT`, narrows this to 16 bits at `0x35498`, and sets transfer status **0 only if it equals the requested count** (`0x3549a..0x354cc`). A mismatch gives status 1 and does not call the residual FIFO copy at `0x354b2`. The parser accepts only status 0 after each command, length, and body receive (`0x331c4..0x331ca`, `0x3324e..0x33252`, `0x33292..0x33296`). The 16-bit narrowing cannot wrap for this caller with a requested count below 49,152 and a configured USB packet of at most 512 bytes, subject to the controller's RXCOUNT reporting its configured packet size. The FIFO-only handler separately keeps status 4 until the accumulated byte count reaches the request (`0x3554e..0x3555a`) and stalls on overrun (`0x35522..0x35530`).

Consequently, a short or zero-length bulk packet is not by itself a completed four-byte command or length. If the host stops after fewer bytes, the ROM waits for more bytes or exits on timeout/error. A packet exceeding the request does not become a second command in the same packet. This conclusion is from the ROM's completion logic and normal controller contract; it does not establish behavior for an undocumented MUSB DMA hardware fault or malformed electrical packets.

The first command wait uses a ROM timer at `0x4a304010`, with USB source default budget `0x18000` ticks (`0x330ec..0x33100`, `0x33192..0x331aa`). The chooser can override that budget from its boot configuration at `0x33102..0x33136`; those fields are not USB packet fields. The length and image waits each use `0x1e0000` ticks (`0x3321e..0x33240`, `0x33274..0x33284`). GET_ID send has its own `0x2666`-tick wait (`0x33078..0x3308e`). These are raw timer counts; no wall-clock duration is inferred here. A zero first-command budget selects an unbounded wait in `0x331ae..0x331b4`, but the default USB budget is nonzero.

## Reset, reconfiguration, and cleanup

USB SET_CONFIGURATION accepts only zero or one. Configuration zero disables the data endpoints and changes USB state to 3 at `0x35798..0x357de`; it does **not** set an active command descriptor's status to successful completion. The ordinary USB bus RESET event (INTRUSB bit 2) sets the USB state byte to 2 at `0x35bb6..0x35bbe` but does not directly complete the pending data descriptor. The branch at `0x35c1c..0x35c32` is different: it handles DEVCTL.BDEVICE becoming clear, resets the controller with `0x35274`, and marks a pending descriptor status 1. The caller accepts only status 0. Reconfiguring during an active transfer can disrupt it; whether a MUSB DMA channel survives a bus RESET and reconfiguration is a hardware question, but the software still uses the originally checked count and fixed destination.

The BDEVICE-loss branch checks the global data-IN descriptor first and skips its data-OUT check if that descriptor is pending (`0x35c20..0x35c32`). This does not leave an independent active data-OUT descriptor pending in the ordinary boot protocol: `0x33058` uses the *same* descriptor as receive, waits for GET_ID's data-IN status 0, and only then arms the next data-OUT receive (`0x331de..0x331f6`). An EP0 control reply has separate state at `0x4030dc48` and does not populate the global data-IN descriptor. After a prior GET_ID, the stale data-IN pointer aliases the active receive descriptor, so marking it status 1 also ends that receive. Before any GET_ID, the data-IN pointer is zero; the BDEVICE-loss branch's first dereference would merit fault-behavior review, but it does not supply a host-controlled address or an observed memory write.

Unknown command, zero or oversized length, transport error, and timeout converge on `0x332c4..0x332d6`. That path invokes the transport close callback if initialized. USB close at `0x340aa..0x340ca` clears the active global pointers/counts, resets endpoint state through `0x35274`, and unregisters the two USB interrupt handlers. It returns failure to the boot-source chooser, which can continue with another configured boot source. The close routine does not explicitly rewrite a timed-out descriptor's pending status, but it removes its global pointer and disables the endpoint before the chooser's stack frame is released. A post-close DMA/interrupt race is a possible hardware question, not a demonstrated write outside the checked buffer.

## After the body: CH and signed-image routing

Only a complete body causes the call at `0x332b6` to `0x32fd6`. That function first scans a 512-byte TOC at the fixed image base (`0x32fe4..0x32fec`). If the first TOC names CHSETTINGS, it invokes the CH handler and advances the image pointer by 512 bytes before scanning a second TOC (`0x32ff0..0x33010`). There is **no additional USB command or second USB body transfer** in this continuation. It is an in-memory parser transition after one BOOT body. The [CH audit](bootrom-ch-parser-2026-11-07.md) shows that CH record offsets are not bounded by the received length before their first read, conditional on the CH fuse gate.

The declared USB length is not passed as an argument to `0x32fd6`; a one-byte body still reaches its TOC scan because `0x33254` rejects only zero. The scanner at `0x3432a..0x34378` can inspect up to sixteen 32-byte TOC entries, so a very short accepted body lets it read stale bytes *beyond that received body* in the fixed SRAM image window. If it recognizes a CH prefix, the second TOC scan starts at base plus 512. This is a genuine length-to-parser mismatch and a route to stale-memory-dependent behavior; the visible path neither sends those bytes back to the host nor derives a writable destination from them. A host can place its own full TOC and CH data within a longer accepted body, which already exposes the separately documented CH pre-authentication configuration surface. No signature bypass follows from shortening the transfer alone.

The chooser at `0x30b92..0x30be6` examines the original command word after the call returns. Its `0xf003xx06` source-selection case is **not a third accepted USB command**: `0x331cc..0x331d6` rejects that value before a body receive. It belongs to the broader boot-source chooser, and no path in the reviewed USB command handler generates it from GET_ID or BOOT. Following a BOOT image, the parser/security chain is entered; a failed image can return control to the chooser, not to a second command receive on that same USB transaction.

### Is there a CH readback or rejection-status oracle?

The trace helper `0x325a4` ORs one bit into a three-word bitmap at `0x4030d040`; `0x32560..0x3259e` initializes and saves that bitmap in adjacent `0x4030d04c..0x4030d054`. It does not send on USB. The GET_ID builder `0x348bc..0x349c2` fills the separate `0x4030db8c` ASIC-ID buffer with ROM/device fields and sets its first byte to the selected source. On later calls, a nonzero first byte skips the builder's initial fill (`0x348e2..0x348ea`); there is no copy from the trace bitmap to the ID response. The only data-IN call in the USB boot command loop is the GET_ID response before BOOT (`0x331de..0x331e4`). After BOOT enters `0x32fd6`, neither its CH status nor its security rejection is serialized to a USB reply. The EP0 dispatcher also offers only the standard bounded requests in the separate [EP0 audit](bootrom-usb-audit-2026-11-07.md).

A CH magic hit, fault, or handler side effect may change boot timing or whether the device reenumerates. That is at most a coarse, reboot-dependent behavior oracle in the visible path. Its comparison values are four fixed CH magics, not host-chosen bytes, and no direct ROM-byte disclosure or arbitrary memory dump follows.

## Assessment and next offline check

The strongest state-machine observation is the accepted `length=1..511` followed by a 512-byte TOC scan without a received-length argument. It is an out-of-received-image **read and parsing** behavior, not a demonstrated ROM disclosure or code-execution path. No short-packet command confusion, repeated-command overwrite, or pre-authentication arbitrary USB DMA destination was found. The exact MLO's 41,024-byte size remains above the type-2 USB BOOT cap.

The remaining uncertainty is the MUSB DMA controller's behavior if the host sends a packet larger than the armed receive count or changes configuration during DMA. A useful next step is an offline check of OMAP4460 MUSB DMA semantics/errata or controller RTL, specifically whether DMA ever writes past the programmed count before ROM `0x35454` compares completion. The ROM disassembly alone cannot prove a hardware overrun, and the existing capture of an oversized upload reports a stall after the first packet rather than evidence of an SRAM write outside the destination.
